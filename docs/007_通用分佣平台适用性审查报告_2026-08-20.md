## 一、结论

| 维度 | 评级 | 依据 |
|------|------|------|
| 作为通用分佣**计算内核**的设计方向 | ★★★★☆ | 分层清晰、纯计算与 IO 分离彻底、原语可组合 |
| 作为通用分佣**平台**的当前完成度 | ★★☆☆☆ | 无账本 / 出款 / 冲正 / 多租户；平台层完全缺失 |
| 计算内核自身的资金安全成熟度 | ★★☆☆☆ | 存在 3 项已实测 P0（封顶失效、等级 fail-open、拆分错分） |
| 当前版本能否直接接客户上生产 | **不能** | 官方结算服务中平台日封顶完全失效，实测 limit=100 → 累计发放 300 |

**一句话定位**：这是一个骨架正确、但尚未完成资金安全硬化的**分佣计算库**，
不是分佣平台。

**最大的风险不是某个 bug，而是预期差**：`README` 与 `docs/005` 自评
「通用性 ★★★★☆ / 韧性 ★★★★★ / 已覆盖 80% 以上常见营销分销返佣场景」，
而包已发布在公网 npm 上。任何团队按此自评直接接入并上线，会在
不报错、不告警的情况下超发资金。文档口径的准确性在此已构成安全问题本身。

## 二、抽象设计评估

### 2.1 做对的部分（应当保留的资产）

**（1）纯计算内核与 IO 彻底分离**
`src/engine/**` 不碰数据库、不管事务。运行时强依赖只有 1 个（`decimal.js`），
`joi` / `sequelize` 均为 `optional peerDependencies`。这个骨架能长期演进。

**（2）`createRuleSetValidation(Joi)` 工厂注入**
由调用方传入 joi 实例，规避跨包 "Cannot mix different versions"。
这是踩过真实坑的人才会做的设计，不是教科书写法。

**（3）`CONFIG_FIELD_KEYS` 冻结常量**
把配置字段名做成单一事实来源，消费方 diff 逻辑不必手写字面量，避免长期漂移。

**（4）金额一律 decimal string**
`Decimal` 包装层统一 28 位精度、`ROUND_HALF_UP`、默认 4 位小数；
`applyBudgetGuard` 的按比例缩减采用最大剩余法，保证缩减后各项之和精确等于预算上限。
资金精度这一层是达标的。

**（5）CI 与发布纪律**
GitHub Actions 覆盖 Node 18/20/22 矩阵，链路为 `npm ci → test → smoke → verify-pack`，
`prepublishOnly` 挂了打包校验。同规模的库里属于上游水平。

### 2.2 抽象的结构性问题

#### 问题 1：奖励目标只有 `SOURCE` / `PARENT`，层级规则外置到了宿主

`distributeByDefs` 的 `target` 白名单只有 `SOURCE`（事件来源人）与 `PARENT`（直接上级），
没有 `ANCESTOR[n]` 之类的层级寻址，也没有 `maxDepth`。

多级固定比例（一级 10% / 二级 5% / 三级 3%）**并非不可实现** —— 用 `LEVEL` 且
不设 `accumulateInChain`（缺省 false，水位不推进）即可，实测：

```js
distributeByDefs({
  event: { sourceNodeId: "u9", eventValue: "1000" },
  ancestors: [{ id:"L1", rankRate:"10" }, { id:"L2", rankRate:"5" }, { id:"L3", rankRate:"3" }],
  rewardDefs: [{ rewardId: "multi", type: "LEVEL" }],   // accumulateInChain 缺省 = false
})
// 实测输出：L1 rate=10% amount=100 / L2 rate=5% amount=50 / L3 rate=3% amount=30  ✅
```

问题在于**比例挂错了地方**：它挂在每个祖先节点的 `rankRate`（等级语义字段）上，
而不是挂在 `rewardDef` 的「层级 → 比例」映射表里。后果有三：

- 「第 N 层拿 X%」这条业务规则无法写进规则集配置，必须由宿主在构造 `ancestors` 时
  按层序逐个把比例塞进节点 —— 规则回流到代码，配置驱动在此处失效。
- 同一条链上无法同时表达「等级分成」与「层级固定分成」，因为二者争用同一个 `rankRate` 字段。
- 无 `maxDepth`：实测传入 8 层祖先即发放 8 层，深度由调用方传入数组长度隐式决定，
  规则集无法声明「最多发 3 层」这一风控边界。

#### 问题 2：`skipRankZero` 默认 true，把比例/固定奖励耦合到了等级模型

`direct-calculator._isRankZero` 判定 `node.rankRate <= 0` 即跳过发放，
而 `skipRankZero` 缺省为 `true`。实测（`distributeByDefs`）：

| 配置 | 结果 |
|------|------|
| `directParent = {id:"u0"}`，DIRECT/PARENT/10% | `[]` — 零发放 |
| `directParent = {id:"u0", rankRate:"10"}`，同上 | `amount = "100"` |
| `directParent = {id:"u0"}`，同上 + `skipRankZero:false` | `amount = "100"` |
| `directParent = {id:"u0"}`，FIXED/PARENT 邀新固定 50 元 | `[]` — 零发放 |

一个「我没有等级体系，只要一级分销 10%」的使用方，按最直觉的配置接入，
结果是**什么都不发、且不报错**。这是最容易撞上的接入陷阱。

同时存在语义不一致：`skipRankZero` 只作用于 `target=PARENT` 分支
（经 `calculateDirect` / `calculateFixed` / `calculateCustom`），
`target=SOURCE` 分支在源码中明确不应用该规则。实测 `CUSTOM/SOURCE amount:"100"`
在节点无 `rankRate` 时正常发放 `"100"`。同一个字段在两个 target 下行为不同。

#### 问题 3：`rewardDef.conditions` 只对事件求值，看不到受益节点

`reward-distributor._meetsRewardCondition(def, event)` 的数据源固定是 `event`
（源码注释已明示「数据源 = 事件对象」）。因此以下这类规则无法配置化：

- 「只给 V2 以上的上级发佣」
- 「上级团队业绩满 5 万才发」
- 「上级本月已达上限则跳过」

条件能力只覆盖了「事件侧」，缺失「受益人侧」，等于砍掉一半。
补法很轻：给 condition 增加 `source: "event" | "target"`，
`condition-evaluator` 已经是通用的、能直接对节点求值（`evaluateTier` 就是这么用的）。

#### 问题 4：多个 `DISTRIBUTE` 阶段互相覆盖，无合并语义

`pipeline-orchestrator` 中每个 DISTRIBUTE 分支都是 `current = distributeByDefs(...)`
直接赋值。想做「先算基础佣金，再叠加活动奖励」必须挤进同一个 DISTRIBUTE 的
`rewardDefs` 数组，阶段编排的组合价值被削掉一部分。
`SPLIT` 还强制必须是最后一个阶段（否则显式抛错，这个防御是对的，
但也说明 SPLIT 的输出类型与其他阶段不同构，是抽象上的一个断层）。

#### 问题 5：「纯函数、零副作用」的对外契约与实现不符

`README.md:84` 写：「**纯函数，零副作用**：所有计算函数不修改输入参数，不查询外部状态」。

实际：
- `applyCaps` 就地 mutate 传入的 `state`（`state.platformPaid = ...`、`state.memberPaid.set(...)`），
  源码注释坦承「裁剪后直接推进水位 state」。
- RANK handler 就地写 `node.rankRate` / `node.rankId`，注释说明这是为了让后续 DISTRIBUTE
  「立即可见」（依赖对象引用）。

副作用本身在这两处是**有意为之且合理的**（水位必须跨记录累积），
问题在于对外宣称了相反的契约。使用方按「零副作用」假设去复用输入对象、
或做并发/重放，就会被反噬。应当修正文档，而不是修改实现。

#### 问题 6：领域词与悬空引用泄漏进已发布源码

`src/` 中含具体客户名的注释 **13 处**，其中 9 处指向
`src/adapters/songrong-reward-adapter.js` —— 该文件在包内不存在
（`ls src/adapters/` 只有 `customer-adapter-template.js`、`index.js`、`rule-set-adapter.js`）。

最讽刺的一处在 `src/index.js:5`：

```
* 不查询数据库，不管理事务，不认识任何业务词（直推/极差/佣金/茸贝）。
```

一个宣称领域无关的公开包，在声明「不认识业务词」的同一行里点名了业务词。
`rank-evaluator.js:80` 还留着「遗留字段模式（兼容层，松茸 vip_tiers 旧映射）」。
对外部使用方而言，这些注释指向的是读不到的上下文，属于纯噪声 + 客户信息外泄。

## 三、已实测的资金安全缺陷

以下每条均可原样复现。所有调用使用源码实际签名。

### P0-1｜平台日封顶在官方结算服务中完全失效 🔴

**根因**：`src/services/generic-settlement.service.js:380` 是全包唯一的
`executePipeline` 调用点，写法为：

```js
const result = engine.Orchestrate.executePipeline({ stages });   // ← 未传 context
```

而 `pipeline-orchestrator.js:49-51` 在 context 缺失时自建初始水位：

```js
if (!context.capState) {
  context.capState = { platformPaid: "0", memberPaid: new Map() };
}
```

于是每个事件的封顶水位都从零重新开始，`CAP` 阶段退化为「单事件内裁剪」。

**实测复现**（规则集 `PLATFORM_DAILY limit = "100"`，DIRECT/SOURCE/100%，连发三单）：

```
订单 A 落账: ["100"]
订单 B 落账: ["100"]
订单 C 落账: ["100"]

PLATFORM_DAILY limit = 100，三单实际累计发放 = 300
预期（封顶生效）= 100，实测 = 300，封顶失效
```

**为什么这不是"使用方用错了"**：`docs/003` 与 `docs/004` 写明「调用方负责保存/恢复 capState」，
但包内唯一的结算服务 `GenericSettlementService` **没有暴露任何 capState 的读写钩子**
（`REQUIRED_CONFIG_KEYS` 与全部可选配置项中均无相关入口），
`_calculate` 也不接受 context 参数。使用方即便读过文档，也无处注入。
这是接口缺失，不是使用错误。

封顶是防刷、防套利、防配置错误超发的最后一道闸。此项单独就足以判定
当前版本不可上生产。

### P0-2｜等级评估 fail-open：漏写 conditions 即全员顶格 🔴

**根因链**：
1. `rankDefSchema.conditions` 是 `.optional()` —— 不写 conditions 是**通过校验的合法配置**。
2. `evaluateTier`：`levelIndex === 0` 直接 `return true`；`conditions` 为空时回退
   「遗留字段模式」，而在既无 `metadata` 也无 `min_*` 字段时全部门槛取 0 → 逐项跳过 → `return true`。
3. `getHighestQualifiedTier` 保留**最后一个**满足者（这本身是 v1.2.0 针对非单调等级配置的
   正确修复，不应回退）。

三者叠加 → 任何节点命中最高等级。

**实测**：

```js
getHighestQualifiedTier(
  { id:"x", directCount:0, teamPerformance:"0" },
  [{ rankId:"V0", levelIndex:0, rankRate:"0" }, { rankId:"V9", levelIndex:9, rankRate:"60" }]
)
// 实测：{"rankId":"V9","levelIndex":9,"rankRate":"60"}   ← 零活跃节点顶格 60% 分成

// 对照（V9 带 conditions）：{"rankId":"V0","levelIndex":0,"rankRate":"0"}   ✅ 正确
```

配置漏写一处，全员直接拿最高分成比例。安全默认必须是 fail-closed：
`levelIndex > 0` 的等级若无任何条件来源，应当校验期报错或求值返回 false。

**加重因素**：`rank-evaluator.js` 分支覆盖率仅 **21.53%**（语句 36%），
是全仓最低的文件之一 —— 缺陷正落在测试盲区里。

### P0-3｜`splitByTargets` 静默错分资金 🔴

**根因**：最后一个 target 无条件领取 `remaining`，且 `ratio` 之和从不校验
（`allocatorSchema` 只校验单个 `ratio >= 0`，无总和约束）。

**实测**（签名为位置参数 `splitByTargets(totalAmount, targets)`）：

| 输入 | 实测输出 | 应有行为 |
|------|---------|---------|
| `("1000", [{A,70}])` | A 得 `"1000"` | 校验失败（合计 70 ≠ 100） |
| `("1000", [{A,30},{B,20}])` | `["300","700"]` | 校验失败（合计 50 ≠ 100） |
| `("1000", [{A,60},{B,60}])` | `["600","400"]` | 校验失败（合计 120 ≠ 100） |

三种情况下 `snapshot` 都如实记录了声明比例（如 `{"A":"30","B":"20"}`），
但实发金额与声明严重不符，**不抛错、不告警**。
B 声明 20% 实得 70%，这是直接的资金错分。

「最后一项补差」的设计动机（消除小数除不尽的尾差）是正确的，
但它必须建立在「比例之和已校验为 100」的前提上，否则补差就变成了吞掉全部剩余。

### P1-1｜封顶可被配置绕过 🟠

`applyCaps` 用 `find` 取**第一条**匹配的 scope：

```js
const platformCap = capDefs.find((c) => c.scope === "PLATFORM_DAILY" && Decimal.gt(c.limit, "0"));
```

实测：

| 场景 | 实测结果 |
|------|---------|
| 同 scope 两条（`limit:"1000"` 在前，`limit:"100"` 在后），记录 500 | `["500"]` — 更严的第二条被静默忽略 |
| 未知 scope `PER_USER_MONTHLY limit:"10"`，记录 9999 | `["9999"]` — 完全不封顶 |

`capDefSchema.scope` 的枚举只有 `PLATFORM_DAILY | PER_USER_DAILY`，
所以未知 scope 会在校验期被拦住 —— 但**仅当使用方真的调用了校验**。
`applyCaps` 自身对未知 scope 是静默放行，纯计算路径（不过 Validation）无任何保护。
Joi 层也没有同 scope 去重校验（只有 `capId` 唯一性）。

### P1-2｜`addBusinessDays` 夏令时日期错位 🟠

`utils/business-date.js` 用 `new Date(dateStr)` + 本地 `setDate()` + `toISOString()`，
在有夏令时的时区会错日。实测：

```
TZ=America/New_York  addBusinessDays("2026-03-07", 1) → "2026-03-08"
TZ=America/New_York  addBusinessDays("2026-03-08", 1) → "2026-03-08"   ← 原地不动
TZ=Asia/Shanghai     addBusinessDays("2026-03-08", 1) → "2026-03-09"   ✅
```

即 NY 时区下 `03-08` 被重复产出、`03-09` 被跳过。结算周期计算、
T+N 冻结解冻日一旦落在 DST 切换日就会错。修法是改为纯 UTC 日期算术
（`Date.UTC` + `setUTCDate`），无需引入依赖。

注：`business-date.js` 语句/分支覆盖率均为 100%，但测试全部跑在
CI 与本地的默认时区下，没有一条跨时区断言 —— 覆盖率数字在此完全没有保护作用。

### P1-3｜官方接入模板本身是坏的，README 示例跑出空结果 🟠

`src/adapters/customer-adapter-template.js` 是 README 推荐给新使用方抄写的参考实现。
实际缺陷：

- `_buildRewardDefs` 传的键是 `id` 而非 `rewardId` → 产出的 RewardDef `rewardId: undefined`，
  落库后无法区分奖励类型、无法对账。
- `accumulateInChain: true` 硬编码，与 `RewardDef` 的缺省值相反，
  会把「多级固定比例」意外变成「极差」（见 §2.2 问题 1 的对照实测：
  同一条 10/5/3 的链，`accumulateInChain:true` 时只有 L1 拿到钱）。
- `_buildRankDefs` 丢弃 `rankRate` → 一律 `"0"`，叠加 `skipRankZero` 默认 true 后全链零发放。

**实测 README「扩展指南」的完整示例**：

```js
executeCustomerIncentive({
  event: { memberId: "user1", amount: "1000", type: "purchase" },
  directParent: { id: "user0", parentId: null, directCount: 10, teamPerformance: "50000" },
  ruleSet: {
    config_json: { pipelineDef: { stages: [{ handler: "DISTRIBUTE" }] } },
    rewardDefs: [{ type: "DIRECT", rate: "10", target: "PARENT" }],
    rankDefs: [{ levelIndex: 1, conditions: [{ type:"COMPARE", field:"directCount", operator:"GTE", value:3 }] }],
  },
})
// 实测：final = []
```

**官方文档的示例代码跑出来是空数组。** 新使用方接入的头 5 分钟就会撞在这里，
而且因为不报错，最可能的结论是「引擎不好用」而非「模板有 bug」。

加重因素：`customer-adapter-template.js` 语句覆盖率 **21.73%**、
**函数覆盖率 0%** —— 这个文件从未被任何测试执行过。

### P2｜其余已确认问题 🟡

| 项 | 位置 | 实测 / 说明 |
|---|---|---|
| `ALERT_ONLY` 边界误判 | `budget-controller.js:55` 用 `Decimal.lt` | `amount="100"` 恰好等于 `limit="100"` 的剩余额度时，实测 `snapshot.payoutCaps` 出现 `alertOnly:true`。恰好用尽额度不是超发，应为 `lte` |

## 四、作为「通用分佣平台」的能力缺口

按分佣业务的重要性排序（不按实现难度）。

### 4.1 退款 / 冲正 / 佣金追回 —— 缺口中最致命的一项

全仓检索 `refund|reversal|revoke|clawback|chargeback|退款|冲正|撤销|追回|回收`：
**`src/` 命中 0 次**，仅 `docs/005` 提及并列为 P2「一期不做」。

电商退单、金融撤单、SaaS 退订都是常态而非异常。没有冲正原语，
意味着「已发佣金」这件事在引擎里是不可逆的，业务层只能自己写反向流水 ——
而这恰恰是最容易算错、最需要引擎保证一致性的部分。
把它排在 P2 是本项目路线图最需要重新评估的判断。

### 4.2 其余缺口

| 缺口 | 现状 | 影响 |
|------|------|------|
| 层级 → 比例映射表 + `maxDepth` | 只能靠节点 `rankRate` 外置表达，无深度上限 | 规则回流宿主代码；无层数风控 |
| 周 / 月 / 活动累计封顶 | 只有 `PLATFORM_DAILY` / `PER_USER_DAILY` | 活动总预算无法控制（`docs/005` 列 P1，未做） |
| 活动期加成、规则生效期 | 规则集是静态配置，无时间维度 | 双十一翻倍、限时奖励无法配置（`docs/005` 列 P1，未做） |
| 多币种 / 多资产 | 单金额维度 | 现金 + 积分 + 券的组合奖励无法表达 |
| 受益人侧条件 | `conditions` 只读事件 | 见 §2.2 问题 3 |
| 钱包账本、可提现余额、T+N 冻结解冻、出款、对账、税务代扣 | 完全不在包内 | 这些才是「平台」二字的主体 |
| 多租户隔离、规则集审批发布流 | 有灰度路由（MD5 hash 加权），无审批/发布/回滚 | 规则变更缺少管控闸门 |
| 事件乱序、补偿、重放 | 只有幂等（预读 + `UniqueConstraintError` 兜底） | 消息乱序场景下水位与等级的最终一致性无保证 |
| 风控反套利 | 无 | 自购、环形推荐、同设备/同支付账号、异常增速一项都没有。分佣系统上线后被薅是必然事件 |

关于账本与出款：**建议明确划到内核之外**（见 §五路线）。
把它们塞进这个包会摧毁它现在最大的优点 —— 纯。

## 附录 B：P0-1 端到端复现脚本

保存到**项目根目录**（如 `verify-p0-cap.js`）后 `node verify-p0-cap.js` 执行。
依赖包内 `demo/mocks/`，不触碰数据库、不写任何持久化存储：

```js
const { GenericSettlementService } = require("./src/services");
const { createMemoryModel } = require("./demo/mocks/memory-model");
const { createMemorySequelize } = require("./demo/mocks/memory-sequelize");
const { createMemoryRuleSetService } = require("./demo/mocks/memory-rule-set-service");

const RULE = {
  rewardDefs: [{ rewardId: "self", type: "DIRECT", target: "SOURCE", rate: "100" }],
  capDefs: [{ capId: "plat", scope: "PLATFORM_DAILY", limit: "100" }],
  pipelineDef: { stages: [{ handler: "DISTRIBUTE" }, { handler: "CAP" }] },
};

const svc = new GenericSettlementService({
  name: "probe", ruleSetCode: "rs",
  model: createMemoryModel({ tableName: "t", uniqueKeys: [["orderNo"]] }),
  sequelize: createMemorySequelize(),
  ruleSetService: createMemoryRuleSetService({ rs: RULE }),
  logger: { info() {}, warn() {}, error() {} },
  buildEvent: (e) => ({ sourceNodeId: e.userId, eventType: "order", eventValue: e.amount }),
  buildRecord: (e, r) => ({ orderNo: e.orderNo, userId: r.nodeId, amount: r.amount }),
  idempotency: {
    buildPreReadWhere: (e) => ({ orderNo: e.orderNo }),
    buildFallbackWhere: (e) => ({ orderNo: e.orderNo }),
  },
});

(async () => {
  let total = 0;
  for (const orderNo of ["A", "B", "C"]) {
    const r = await svc.settle({ orderNo, userId: "u1", amount: "100" });
    const amounts = (r.data?.lines || []).map((l) => l.amount);
    total += amounts.reduce((s, a) => s + Number(a), 0);
    console.log(`订单 ${orderNo} 落账:`, JSON.stringify(amounts));
  }
  console.log(`\nlimit = 100，三单实际累计发放 = ${total}`);
})();
```

## 附录 C：给决策者的一页结论

**能不能作为通用分佣平台？现在不行。** 但骨架值得继续投。

底子是对的：分层、纯计算、配置驱动、decimal 精度、joi 工厂注入、CI 矩阵。
问题集中在两类：

- **安全默认取反了** —— 封顶失效、等级 fail-open、拆分吃余额，共同特征是
  「配置写错或漏写 → 不报错 → 直接多发钱」。这类问题的修复成本低（1–2 周），
  但不修就不能碰真实资金。
- **原语没覆盖行业刚需** —— 冲正是第一位，层级比例表配置化是第二位。
  这决定它能否真正做到「不改代码接第 5 到第 10 个客户」（1–2 个月）。

平台级能力（账本、出款、多租户、风控）建议明确划到内核之外单独立包，
否则会失去它现在最大的优点 —— 纯。
