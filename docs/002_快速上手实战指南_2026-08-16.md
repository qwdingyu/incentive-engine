## 二、三步接入

### 步骤 1：定义规则集

规则集是引擎的"配置文档"，描述了完整的激励方案：

```js
const ruleSet = {
  rewardDefs: [
    // 本人收益：事件来源节点拿 100%
    { rewardId: "self", type: "DIRECT", target: "SOURCE", rate: "100" },
    // 推荐人奖励：直接上级拿 5%
    { rewardId: "referral", type: "DIRECT", target: "PARENT", rate: "5", skipRankZero: false },
  ],
  rankDefs: [
    { rankId: "MEMBER", levelIndex: 0, conditions: [] },
  ],
  capDefs: [
    // 单用户日封顶 5000
    { capId: "user_day", scope: "PER_USER_DAILY", limit: "5000", onExceed: "REJECT" },
  ],
  allocators: [
    { allocatorId: "full_liquid", type: "PERCENTAGE_SPLIT", targets: [{ target: "LIQUID", ratio: 100 }] },
  ],
  pipelineDef: {
    stages: [
      { id: "distribute", handler: "DISTRIBUTE" },
      { id: "budget", handler: "OVER", config: { totalBudget: "200", onExceed: "CAP" } },
      { id: "cap", handler: "CAP" },
    ],
  },
};
```

### 步骤 1.5：校验规则集配置（可选，推荐）

引擎提供 joi 校验工厂函数，用于验证规则集配置的合法性：

```js
const Joi = require("joi");
const { createRuleSetValidation } = require("@usethink/incentive-engine").Validation;
const { ruleSetConfigSchema } = createRuleSetValidation(Joi);

const { error } = ruleSetConfigSchema.validate(ruleSet);
if (error) {
  console.error("配置校验失败:", error.message);
  // 在写入 DB 前拦截非法配置
}
```

> ⚠️ `createRuleSetValidation(Joi)` 需要调用方传入自己的 joi 实例，避免 joi 跨包版本不一致导致的 `"Cannot mix different versions"` 错误。

### 步骤 2：写入 DB（可选，推荐）

规则集可存入 DB（如 `incentive_rule_sets` 表），通过管理端 API 配置，运行时热加载。

### 步骤 3：调用引擎计算

```js
const engine = require("@usethink/incentive-engine");

// 构造事件 + 网络
const event = { sourceNodeId: "user1", eventValue: "1000" };
const directParent = { id: "referrer1", rankRate: "10" };
const ancestors = [{ id: "agent1", rankRate: "5" }, { id: "agent2", rankRate: "2" }];

// 方式 A：直接分发（跳过流水线，适合简单场景）
const records = engine.Distribute.distributeByDefs({
  event, directParent, ancestors,
  rewardDefs: ruleSet.rewardDefs,
});

// 方式 B：通过流水线（推荐，完整链路）
const stages = engine.Adapters.buildPipelineStages(ruleSet, { event, directParent, ancestors });
const { final, context } = engine.Orchestrate.executePipeline({ stages });
```

## 三、三个真实接入示例

### 3.1 电商一级分销

```js
// 规则集：ecommerce_demo（DB 配置）
// 事件：订单支付
// 奖励：直接上级 10%
// 封顶：单用户日 5000
// 接入成本：~40 行配置 + 自有落账表 + Model
const { GenericSettlementService } = require("./generic-settlement.service");
const { ecommerceConfig } = require("./customer-configs");
const settlement = new GenericSettlementService(ecommerceConfig);
const result = await settlement.settle({
  orderNo: "ORD001",
  buyerId: "buyer1",
  sellerId: "seller1",
  amount: "1000",
});
```

### 3.2 金融返佣

```js
// 规则集：finance_rebate_v1（DB 配置）
// 事件：交易成交
// 奖励：直接上级 0.5% + 代理链 0.3%
// 接入成本：~50 行配置 + 自有落账表 + Model
const settlement = new GenericSettlementService(financeRebateConfig);
const result = await settlement.settle({
  tradeNo: "TRD001",
  traderId: "trader1",
  tradeAmount: "10000",
  referrerId: "referrer1",
  agents: [{ agentId: "agent1", rate: "0.3" }],
});
```

### 3.3 返利商城（本人返利 + 预算兜底）

```js
// 规则集：cashback_v1（DB 配置）
// 事件：买家支付
// 奖励：买家本人返利 10% + 推荐人奖励 10%
// 预算兜底：总奖励不超过订单金额的 10%
// 接入成本：~60 行配置 + 自有落账表 + Model
const settlement = new GenericSettlementService(cashbackConfig);
const result = await settlement.settle({
  orderNo: "ORD001",
  buyerId: "buyer1",
  orderAmount: "500",
  referrerId: "referrer1",
});
```

## 四、接入模式总结

| 接入模式 | 适用场景 | 工作量 | 引擎改动 |
|---------|---------|--------|---------|
| **纯 DB 配置** | 新行业/新玩法，标准 DIRECT/LEVEL 组合 | 建表 + Model + 配置 | 0 |
| **代码适配 + 配置** | 需自定义流水线阶段的复杂场景 | 适配器 + 配置 | 0 |
| **自定义 handler** | 引擎未覆盖的特殊计算逻辑 | 适配器 + 注册 handler | 0（Orchestrate 可扩展） |
