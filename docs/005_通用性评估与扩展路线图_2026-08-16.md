## 一、通用性评估：5-10 个营销/拉新/分佣项目的底座能力

### 1.1 已覆盖的能力矩阵

| 能力 | 说明 | 适用场景 | 覆盖率 |
|------|------|---------|--------|
| **DIRECT 百分比奖励** | 按 eventValue 的百分比给本人(SOURCE)、直接上级(PARENT) 或祖先链定点层(ANCESTOR) | 本人收益、直推佣金、一级分销 | ✅ 已实现 |
| **LEVEL 链式水位差** | 按祖先链 rankRate 逐级差额分配 | 团队极差、多级代理、链式佣金 | ✅ 已实现 |
| **LEVEL 按层固定比例** | `RewardDef.levelRates` 第 n 层拿第 n 个比例（不看 rankRate） | 一级 10%/二级 5%/三级 3% 多级分销 | ✅ 已实现（v4.0.0） |
| **链式层数上限** | `RewardDef.maxDepth` 限制参与计算的祖先层数（非法值抛错） | 深度风控、限制多级层数 | ✅ 已实现（v4.0.0） |
| **定点单层发放** | `target:"ANCESTOR"` + `ancestorLevel` 只给祖先链第 n 层这一个节点发 | 只给第 3 层发 3%、指定层级奖励 | ✅ 已实现（v4.0.0） |
| **FIXED 固定金额奖励** | 按固定金额发放（与事件值无关）给本人/直接上级 | 拉新奖励、人头奖励、固定红包 | ✅ 已实现（v3.1.0） |
| **CUSTOM 动态金额奖励** | amount 常量 + amountFrom 动态取数 | 注册送积分、按事件属性取数 | ✅ 已实现（v3.3.0） |
| **条件奖励过滤（事件侧）** | rewardDef.conditions 按 event.attrs 评估，不满足跳过 | 仅高额订单发佣金 | ✅ 已实现（v3.4.0） |
| **条件奖励过滤（受益人侧）** | `conditions[].source: "target"` 读受益节点字段；LEVEL 逐层求值，被拦下的层不推进水位 | 只给 V2 以上上级发佣、上级团队业绩满 5 万才发 | ✅ 已实现（v4.0.0） |
| **平台日封顶** | 当天平台总发放上限 | 企业预算控制 | ✅ 已实现 |
| **单用户日封顶** | 当天单个用户收到上限 | 防刷、防套利 | ✅ 已实现 |
| **周/月/活动总量封顶** | `scope` = `<维度>_<周期>` 全组合（`PLATFORM`/`PER_USER` × `DAILY`/`WEEKLY`/`MONTHLY`/`TOTAL`），水位按 `state.periods` 分桶 | 活动预算月上限、单用户活动期总量上限 | ✅ 已实现（v4.0.0） |
| **封顶超发策略** | onExceed: REJECT（丢弃）/ ALERT_ONLY（保留+告警标记） | 超发仅告警 vs 超发丢弃 | ✅ 已实现（v3.4.7） |
| **预算兜底保护** | 按 eventValue 比例设总预算上限 | 活动预算控制、防配置错误超发 | ✅ 已实现（CAP/WARN/REJECT） |
| **预算缩减精度** | 最大剩余法保证缩减后求和精确等于预算上限 | 防累积超发 | ✅ 已实现（v3.4.8） |
| **百分比拆分** | 按比例拆分金额（最后一项补差） | 70/30 拆分、多科目分配 | ✅ 已实现 |
| **比较分配** | MAX/MIN/FIRST 多金额比较 | 保底/封顶/取最优 | ✅ 已实现 |
| **等级评估** | 条件驱动的等级晋升 | VIP 等级、代理等级 | ✅ 已实现 |
| **复合条件** | AND/OR/NOT 组合条件树（GTE/GT/LTE/LT/EQ/NE 操作符） | 复杂晋升条件 | ✅ 已实现（NE 于 v3.4.7） |
| **流水线编排** | 任意组合阶段 | 灵活的计算链路 | ✅ 已实现 |
| **灰度/A-B 测试** | Hash 加权版本路由 | 规则集灰度发布 | ✅ 已实现（Utils） |
| **配置校验** | joi schema 校验 | 防非法配置 | ✅ 已实现（Validation） |
| **冲正（REVERSAL）** | `Reverse.reverseRecords` 按比例反向追回已发放收益，产出负金额记录（ROUND_DOWN 截断、累计不超原额、重复冲正幂等） | 退款、撤单、佣金追回 | ✅ 已实现（v4.0.0） |
| **冲正落账编排** | `GenericSettlementService.reversal` 配置块 + `reverse()`（计算在事务内、幂等键独立、不回退封顶水位） | 退款回调一键追回 | ✅ 已实现（v4.0.0） |
| **高精度金额** | decimal.js 28 位精度 | 资金安全 | ✅ 已实现 |

```

  （百分比 + 固定金额双维度；target 的层级表达力已于 v4.0.0 补齐）

快速开发评级：★★★★☆（4/5）

- GenericSettlementService 消除了大部分重复编排代码

```

## 二、能力缺口与扩展路线图

### 2.1 缺口 1：FIXED 固定金额奖励（✅ 已解决 v3.1.0）

**场景**：拉新奖励（拉一人奖 50 元）、人头奖励、固定红包

**当前状态**：已实现。引擎新增 `type: "FIXED"` + `fixedAmount`，`distributeByDefs` 支持 SOURCE/PARENT 两种 target，`calculateFixed` 提供单条计算，`ruleSetConfigSchema` 对 FIXED 类型强制校验 `fixedAmount > 0`（防误配）。

**实现内容**（本次落地）：
1. `RewardDef` 增加 `fixedAmount` 字段（DIRECT/LEVEL/FIXED/CUSTOM 四类型）
2. `direct-calculator.js` 新增 `calculateFixed` 函数（金额与事件值无关，沿用 skipRankZero 语义）
3. `distributeByDefs` 增加 FIXED 类型处理（SOURCE/PARENT + 未知 target 抛错）
4. `ruleSetConfigSchema` 允许 FIXED 类型，并通过 `.custom` 交叉校验强制 `fixedAmount > 0`
5. 引擎测试新增 9 例（6 个 distribute + 3 个 validation），170 全绿

**示例配置**：
```js
{
  rewardId: "referral_bonus",
  type: "FIXED",
  target: "PARENT",
  fixedAmount: "50",       // 固定金额 50 元
  skipRankZero: false,
}
```

### 2.2 缺口 2：WEEKLY/MONTHLY/活动总量 封顶（✅ 已解决 v4.0.0）

**场景**：活动预算（周/月上限）、单用户活动期总量上限、运营周期控制

**当前状态**：已实现。`scope` 从 2 个固定值扩展为 `<维度>_<周期>` **全组合 8 个**：
`PLATFORM` / `PER_USER` × `DAILY` / `WEEKLY` / `MONTHLY` / `TOTAL`，
并导出 `Allocate.CAP_SCOPES` 常量供宿主配置后台直接引用。

**关键设计（必须理解，否则会误以为引擎管周期边界）**：**引擎不认识日期**。
`PLATFORM_DAILY` 之所以是「日」封顶，靠的是宿主那行水位按业务日存、跨天自然归零；
引擎侧四个周期的唯一差别是**水位分桶的键**。因此周期边界仍由宿主决定
（`biz_week` / `biz_month` / `campaign_id` 各自一行）。「活动总量封顶」故意**不做成单独 scope**
（`CAMPAIGN_TOTAL` 是领域概念），而是 `PLATFORM_TOTAL` / `PER_USER_TOTAL` + 一行活动期内不归零的水位。

**本次落地**（v4.0.0）：

1. `budget-controller.js`（2.4.0）新增 `CAP_DIMENSIONS` / `CAP_PERIODS` / `CAP_SCOPES`
   与 `_splitScope` / `_getPeriodBucket` / `_memberMap` / `_memberPaidOf`；`applyCaps` 改为
   按 `CAP_SCOPES` 固定顺序遍历「生效封顶」，最终金额 = `min(原金额, 各生效维度剩余额度)`
2. 水位 `state` 向后兼容：`DAILY` 仍复用顶层 `platformPaid` / `memberPaid`（**唯一存放处**，
   绝不重复写进 `periods` —— 重复状态被宿主只存一半时失败方向是超发），
   其余周期落在 `state.periods[周期]`，且**只在该周期真的配了封顶时才创建**
3. `snapshot.payoutCaps` 新增 `limits`（每个生效 scope 的额度）/ `boundBy`（实际裁剪它的 scope）/
   `alertOnlyScopes`；legacy 字段一位不改，老宿主对账口径不破
4. fail-closed：配了 `PER_USER_*` 但水位缺可用 `memberPaid` Map 时**抛错**，绝不按 0 起算
   （按 0 起算等于把用户额度重新打开 = 超发）
5. **服务层强约束**：`GenericSettlementService._calculate` 对非 `_DAILY` 周期封顶要求成对配置
   `loadCapState` / `saveCapState`，缺任一个直接返回 `{ success:false }` 并指名缺哪一个 ——
   没有水位钩子时「月封顶 5 万」退化成「单事件封顶 5 万」，跑 100 单发 500 万，
   属于比不配封顶更危险的**虚假保障**。`DAILY` 维持历史行为，既有接入方零影响
6. `capDefSchema.scope` 直接 `valid(...CAP_SCOPES)`（校验层引用引擎常量，枚举不会漂移）；
   `src/index.d.ts` 新增 `CapDimension` / `CapPeriod` / `CapScope` / `CapPeriodBucket` / `CapState.periods`

**示例配置**：
```js
capDefs: [
  { capId: "plat_month", scope: "PLATFORM_MONTHLY", limit: "50000" },  // 平台月预算 5 万
  { capId: "user_total", scope: "PER_USER_TOTAL",   limit: "800" },    // 单用户活动期总量 800
]
// 水位行：biz_month=2026-08 一行、campaign_id=1111_dbl11 一行（后者活动期内不归零）
```

**兼容性说明**：`DAILY` 行为逐位不变（源码改完、未加新测试前全量 380 例即全绿，是最强证据）。
唯一的行为变化方向：若此前误写过 `PER_USER_MONTHLY` 这类 scope（3.4.x 静默忽略 = 等于没配封顶），
升级后会真正生效、发放金额变小 —— 这是它本该有的行为，但升级前请核对总额。

**测试**：新增 17 例（引擎 `applyCaps` 多周期 11 + 配置校验 2 + 服务层水位钩子约束 4），
当前 397 全绿；`scripts/smoke-business.js` 新增月封顶端到端链路（四单每单 100、月限 250 →
累计恰好 250，水位落在 `periods.MONTHLY`；缺钩子直接拒绝）。

### 2.3 缺口 3：活动期加成 + 规则集生效期（✅ 已解决 v4.0.0）

**背景**：v4.0.0 之前引擎**没有任何时间概念** —— `campaignDefs` / `effective` 是未识别字段
（`ruleSetConfigSchema` 直接拒绝），「双十一佣金翻倍」「开业首周 1.5 倍」「这套规则只在
活动期内生效」只能由宿主在调用引擎前自己乘系数、自己判过期。而这三件事宿主各自实现时
出错方向全是**超发**：① 系数乘在封顶**之后**（日限额形同虚设）；② 两个活动窗口重叠时
相乘（数倍超发）；③ 过期规则集静默按原比例继续发（双十一的翻倍一直发到十二月）。
docs/007 §一·补 第 15 项把它列为「时间维度缺失」缺口。

**本次落地**（v4.0.0）：

1. 新增 `src/utils/instant-window.js`（`parseInstant` / `isWithinWindow`）：引擎只认
   **绝对时刻** —— `Date` 实例或**带显式偏移量**的 ISO-8601。显式拒绝三类静默算错时刻的输入：
   `"2026-11-11T00:00:00"`（无偏移量 → V8 按**进程本地时区**解析）、`"2026-11-11"`（纯日期 →
   V8 按 **UTC** 解析，与前者口径**相反**）、数字时间戳（秒/毫秒无法区分，传秒落到 1970 年 →
   窗口永不命中）。窗口一律**左闭右开 `[startAt, endAt)`**，两端都必填（开口窗口 = 永久翻倍）
2. 新增 `src/engine/allocate/campaign-multiplier.js`：`applyCampaign(records, campaignDefs, { occurredAt })`
   → `{ records, summary }`（与 `reverseRecords` 同形）。命中活动的记录是**新对象**
   （`snapshot.campaign` 带 `campaignId` / `multiplier` / `originalAmount` / `boostedAmount` /
   `occurredAt` / `window`），未命中的原样透传；另有 `resolveActiveCampaigns` 供配置后台展示
   「当前生效活动」，与 `CAMPAIGN_MULTIPLIER_MAX`（= 10）
3. `pipelineDef` 新增 `CAMPAIGN` handler，汇总写入 `context.campaignSummary`；
   **必须排在 `DISTRIBUTE` 之后、`CAP` / `OVER` 之前**，一条流水线最多一个 —— 三处同时把守：
   `executePipeline` 抛错、`ruleSetConfigSchema` 配置期拒绝（含「配了 `campaignDefs` 却没有
   `CAMPAIGN` 阶段」这类静默失效）、`buildPipelineStages` 的缺省流水线在存在 `campaignDefs` 时
   **自动插入** `DISTRIBUTE → CAMPAIGN → CAP`
4. fail-closed 约束：`multiplier` 是**倍数不是百分比**且 `0 < m <= 10`（把「100%（即不加成）」
   误写成 `100` 会被当场拒绝，而不是放大 100 倍）；加成金额一律 `ROUND_DOWN` 截断到 4 位；
   一条记录被**多个活动同时命中抛错**（相乘是数倍超发，静默取一条等于悄悄改钱），静态可判的
   窗口重叠（`rewardIds` 有交集且窗口相交）在**配置期**即被拒；`rewardIds` 省略 = 全部奖励项，
   写空数组抛错（语义与省略相反）；负金额 / `direction: "REVERSAL"` 的记录进入加成抛错
5. 规则集新增 `effective` 生效期；`GenericSettlementService` 新增可选钩子 `buildOccurredAt(event)`
   （缺省读 `businessEvent.occurredAt`）。引擎**绝不调用 `Date.now()`** —— 结算重试、补跑昨天的单、
   对账重算都在活动窗口之外执行，用「现在」判定等于给历史订单套上今天的系数。取不到时刻、
   时刻不在 `effective` 内、时刻或窗口非法，三种情况都返回 `{ success: false }` 且
   **不开事务、不落任何记录**

**示例配置**：
```js
{
  effective: { startAt: "2026-11-01T00:00:00+08:00", endAt: "2026-12-01T00:00:00+08:00" },
  campaignDefs: [{
    campaignId: "dbl11",
    startAt: "2026-11-11T00:00:00+08:00",
    endAt:   "2026-11-12T00:00:00+08:00",  // 左闭右开：11-12 00:00:00 当刻已不在活动内
    multiplier: "2",                       // 倍数：2 = 翻倍（不是百分比）
    rewardIds: ["referral"],               // 可选，限定加成范围；省略 = 全部奖励项
  }],
  // 不写 pipelineDef 时适配层自动装配 DISTRIBUTE → CAMPAIGN → CAP
}
```

**兼容性说明**：**纯新增能力**，未配置 `campaignDefs` / `effective` 的既有规则集行为零变化
（不需要 `occurredAt`，也不新增任何时间校验）。

**测试**：新增 43 例（引擎/流水线/适配/校验 35 + 服务层 8），并新增 `scripts/smoke-business.js`
第 7 段端到端链路（**故意不写 `pipelineDef`**，验证自动装配：100 → 翻倍 200 → 封顶 150，
落库行带 `campaignId=dbl11`；窗口外发 100 且无活动快照；过期规则集零落库；缺时刻指名
`buildOccurredAt`；无偏移量时刻被拒）。当前 440 全绿。

### 2.4 缺口 4：退款/撤销冲正（REVERSAL）（✅ 已解决 v4.0.0）

**场景**：订单退款 / 撤单 → 按比例回收已发放佣金

**当前状态**：已实现。引擎新增 `Reverse` 命名空间（`reverseRecords` + `REVERSAL_DIRECTION`）、
流水线 `REVERSE` 阶段、`GenericSettlementService` 的 `reversal` 配置块与 `reverse()` 入口。
docs/007 §一·补 曾把本项判定为「通用分佣平台最致命缺口」——
宿主各自反向记账必然出现口径分叉，而出错方向都是**超额扣款**（直接从用户账上多扣钱）。

**本次落地**（v4.0.0）：

1. `src/engine/reverse/reversal-calculator.js`：`reverseRecords({ originalRecords, ratio |
   (reversalValue + originalEventValue), reversedMap, onExceed, reasonCode })` →
   `{ records, summary }`。引擎**不查库**：「哪些记录属于这笔退款」「已冲正多少」全由宿主入参提供
2. 记录形状同时满足两种记账口径：`amount` 为**负数**（宿主 `SUM(amount)` 即净发放额，无需
   `CASE WHEN`）、`reversedAmount` 为正数绝对值、`direction: "REVERSAL"`、`originalRecordId`，
   `snapshot.reversal` 带 `originalAmount` / `alreadyReversed` / `remainingBefore` / `ratio` /
   `basis`（`"RATIO"` 或 `"EVENT_VALUE"`）/ 可选 `clamped` / `reasonCode` 完整对账快照
3. fail-closed 方向与发放侧相反但同源 —— **「宁可少追回，不可超额追回」**：
   金额一律 `ROUND_DOWN` 截断到 4 位；**冲正比例没有缺省值**（两种口径二选一且必须恰好一种，
   都不传抛错，绝不默认 100%）；累计冲正额**永不超过原始发放额**（`reversedMap` +
   `onExceed: "CLAMP"` 裁剪并标记 / `"REJECT"` 抛错）；已全额冲正不再产出第二条；
   传入负金额 / `direction: "REVERSAL"` 的记录抛错（对冲正再冲正 = 反向发钱）
4. 防线（关键）：`applyCaps` / `applyBudgetGuard` **拒绝**负金额与 `REVERSAL` 记录 ——
   负金额会反向推进封顶水位、释放当日预算，「下单发佣 → 退款 → 再下单」即可套出超额佣金。
   封顶水位**默认不随冲正回退**（最安全口径）
5. `executePipeline` 的 `REVERSE` 阶段：与 `DISTRIBUTE` 互斥（两个顺序都抛错）、一条流水线最多
   一个、必须是第一个产出记录的阶段，汇总写入 `context.reversalSummary`
6. `REVERSE` **故意不在 `ruleSetConfigSchema` 的 handler 白名单内**：冲正需要运行期的原始收益
   记录，静态规则集声明必然缺 `originalRecords` 而在计算期抛错
7. `GenericSettlementService.reverse()` 与 `settle()` 的三处**有意差异**：计算在**事务内**
   （金额取决于库里当前值，需在 `loadOriginalRecords` 加行锁防并发超额追回）、幂等键**独立**
   （按退款单号，复用订单号会把第二次部分退款误判为重复回调而漏追回）、**不回退封顶水位**
   且只调 `reversal.postProcess`（复用发放侧 `postProcess` 会把冲正行当作新发放二次计入）

**示例配置**：
```js
// 纯计算：退 300 / 订单 1000 → 按 30% 追回
const { records, summary } = engine.Reverse.reverseRecords({
  originalRecords: [{ recordId: 9001, nodeId: "user0", amount: "100", rewardId: "referral" }],
  reversalValue: "300", originalEventValue: "1000",
  reversedMap: new Map([[9001, "0"]]), reasonCode: "REFUND",
});
// records[0] = { nodeId: "user0", amount: "-30", reversedAmount: "30", direction: "REVERSAL", ... }
```

**兼容性说明**：**纯新增能力**，不冲正的既有接入方行为零变化；
唯一的破坏性方向是 `applyCaps` / `applyBudgetGuard` 开始拒绝负金额记录 ——
若此前把自行构造的负金额行喂进封顶阶段，升级后会显式报错（那本就在反向推进水位、导致后续超发）。

**测试**：新增 43 例（引擎侧 `Reverse` 用例组 25 + 服务侧 `reverse` 用例组 18），当前 380 全绿；
`scripts/smoke-business.js` 新增冲正端到端链路（发放 100 → 30% 退款净 70 → 同一退款单重复回调
幂等 → 二次「全额」退款按剩余裁剪至净 0 → 第三次退款 `skipped`），用内存 Model 真跑账。

### 2.6 补充能力：RANK 等级评估纳入标准流水线（✅ 已解决 v3.2.0）

**背景**：v3.2.0 之前，等级评估（rankRate 推导）不是流水线的一环——宿主必须在调用引擎前

**本次落地**（v3.2.0，与 FIXED 同级为 P0 必备项）：
1. `RewardDef` 的 `rankRate` 语义落地：`model/rank-def.js` 新增可选 `rankRate` 字段（等级关联分成比例，RANK 命中时写入节点）

4. `rule-set-adapter.js` 新增 `RANK` 阶段装配：自动注入规则集 `rankDefs`，默认评估 `directParent + ancestors`

5. 流水线示例：`RANK → DISTRIBUTE → CAP`（DISTRIBUTE 的 LEVEL 链式差额直接消费 RANK 写入的 rankRate）

**示例配置**：

// pipelineDef.stages 声明 RANK 后，等级评估即成为标准流水线一环
{

    { handler: "RANK" },                                // 评估 directParent+ancestors，写入 rankRate

**兼容性说明**：RANK 为**可选阶段**——仅当 `pipelineDef.stages` 声明 `handler: "RANK"` 才启用；

### 2.8 补充能力：链式层数上限 + 多 DISTRIBUTE 合并语义（✅ 已解决 v4.0.0）

**背景**：docs/007 的探针实测发现两条**静默失败**路径，方向恰好相反、都无告警：

1. `RewardDef.maxDepth` 是**未识别字段、被静默忽略** —— 8 层递增 `rankRate` 的祖先链在
   `maxDepth: 2` 与不传时产出完全一致（8 条、金额相同）。配了深度上限却毫无作用，
   链路多深就发多深，属于静默**多发**（深度风控失效）。
2. 流水线里第 2 个 `DISTRIBUTE` **静默覆盖**第 1 个的全部产出 —— 两阶段各产 1 条时
   `final` 只剩后者。配了两组奖励只发一组，属于静默**少发**（记录消失，对账极难定位）。

**本次落地**（v4.0.0）：

1. `chain-calculator.js` 实现 `maxDepth`：按**祖先链位置**截断（`1` = 最近的祖先，
   被 `diffRate<=0` 跳过的层同样占一层），超出层完全不参与计算、也不推进链式水位；
   缺省不限层数（与 3.4.x 一致）；非法值（`0`/负数/小数/非数字）抛错而非静默忽略
2. LEVEL 记录的 `snapshot.depth` 新增层号，便于对账与深度回溯
3. `reward-def.js` 落地 `maxDepth` 字段（`Number()` 归一，未配置为 `null`）
4. `ruleSetConfigSchema` 校验 `maxDepth` 为 `>=1` 整数，并拒绝把它挂在非 `LEVEL` 类型上
   （挂了不会生效，等于让配置方误以为深度受限）
5. `pipeline-orchestrator.js`：第 2 个及以后的 `DISTRIBUTE` 必须显式声明
   `config.merge`（`"append"` 累加 / `"replace"` 显式丢弃），缺省抛错；
   并新增 `RANK` 排在已产出记录的阶段之后即抛错（`RANK` 输出空数组会把前序记录清空 → 零发放）

**示例配置**：
```js
// LEVEL 限 5 层
{ rewardId: "team_diff", type: "LEVEL", accumulateInChain: true, maxDepth: 5 }

// 两组奖励并存
{ stages: [
  { handler: "DISTRIBUTE", config: { rewardDefs: groupA } },
  { handler: "DISTRIBUTE", config: { rewardDefs: groupB, merge: "append" } },
  { handler: "CAP", config: { capDefs } },
] }
```

**兼容性说明**：单 `DISTRIBUTE` 流水线与未传 `maxDepth` 的配置行为零变化。
若此前误传过 `maxDepth`（当时无效），升级后深度上限会真正生效、发放金额变小 ——
这是它本该有的行为，但升级前请核对总额。

**测试**：新增 13 例（maxDepth 计算 5 + 流水线顺序/合并 5 + 配置校验 3），当前 291 全绿。

### 2.9 补充能力：LEVEL 按层固定比例 levelRates（✅ 已解决 v4.0.0）

**背景**：v4.0.0 之前 LEVEL 只有**一种**口径 —— 按节点 `rankRate` 做水位差（极差）。
发放比例取决于节点**自身等级**，而不是它离事件源的**距离**。因此
「一级 10%、二级 5%、三级 3%」这类最常见的多级分销结构无法配置化表达：
宿主只能反过来给每个等级凑 `rankRate`，而一旦等级与层数不是一一对应（同一等级出现在
不同层、或同层节点等级不同）就凑不出来。docs/007 §一·补 把它与 `ANCESTOR[n]`
并列为「target/层级表达力」缺口的两半。

**本次落地**（v4.0.0）：

1. `RewardDef` 新增 `levelRates`（百分比整数数组，索引 0 = 最近的祖先），
   `chain-calculator.js` 拆出 `_calculateByLevelRates`：第 n 层拿 `levelRates[n-1]`，
   不读 `rankRate`、不推进水位、各层相互独立
2. 比例表长度即**隐式深度上限**；与显式 `maxDepth` 并存时取更严的一方
   （有效层数 = `min(levelRates.length, maxDepth)`）
3. 比例为 `0` 的层不发放但**仍占一层**（层号由链位置决定，不因跳过而前移），
   `snapshot.depth` 记录层号，`snapshot.mode: "LEVEL_RATES"` 供对账辨识两套口径
4. fail-closed 约束：与 `accumulateInChain: true` **互斥并抛错**（水位差与按层固定比例
   发放总额不同，静默择一等于悄悄改钱）；空数组 / 含负数、非数字、空值的元素 /
   全为 `0` 一律抛错，不静默零发放
5. `ruleSetConfigSchema` 同步拦截（元素 0~1000 且不允许空洞、全 0 拒绝、
   与 `accumulateInChain` 并存拒绝、挂在非 `LEVEL` 类型上拒绝），
   校验期通过 ⇒ 计算期不会因 `levelRates` 抛错

**示例配置**：
```js
// A. 水位差（缺省口径）：每层拿「自身 rankRate − 下方已发水位」的差额 —— 极差
{ rewardId: "team_diff", type: "LEVEL", accumulateInChain: true }

// B. 按层固定比例：一级 10%、二级 5%、三级 3%（第 4 层及以后不发）
{ rewardId: "multi_level", type: "LEVEL", levelRates: ["10", "5", "3"] }
```

**兼容性说明**：**纯新增能力**，未配置 `levelRates` 的既有规则集行为零变化
（`levelRates: null` / 省略均回落水位差口径）。

**测试**：新增 12 例（按层比例计算 8 + 配置校验 4），当前 303 全绿。

### 2.10 补充能力：target="ANCESTOR" 定点单层发放（✅ 已解决 v4.0.0）

**背景**：v4.0.0 之前 `target` 只有 `SOURCE` / `PARENT`，写 `ANCESTOR` 直接抛
「未知 target」。因此「只给祖先链第 3 层这一个节点发 3%」这类**定点单层**结构
无法表达 —— 宿主只能用 `levelRates: ["0","0","3"]` 近似，但那语义上仍是链式遍历
（产出多条 0 元候选做层号占位），对账口径不清晰，而且和「真的要多级发放」的配置
长得一模一样。§2.9 与本节合起来才补齐 docs/007 §一·补 所指的「target/层级表达力」缺口。

**本次落地**（v4.0.0）：

1. `target` 新增合法值 `ANCESTOR`，`RewardDef` 新增 `ancestorLevel`（>=1 整数，
   `1` = 最近的祖先，层号口径与 `maxDepth` / `levelRates` 完全一致）
2. `reward-distributor.js` 新增 `_resolveAncestorLevel` / `_pickAncestor` /
   `_tagAncestorRecord` 三个私有辅助，从 `ancestors[ancestorLevel - 1]` 取目标节点后
   **复用**既有 `calculateDirect` / `calculateFixed` / `calculateCustom`（三个计算器零改动），
   因此 `DIRECT` / `FIXED` / `CUSTOM` 一次性全部支持，且 `skipRankZero` 语义与 `PARENT` 一致
3. 只产出**一条**记录；`snapshot` 追加 `target: "ANCESTOR"` 与 `ancestorLevel` / `depth`
   （`depth` 与 LEVEL 记录同名同义），两套按层寻址的原语可统一对账
4. fail-closed 约束：`ancestorLevel` 缺失或非法（`0` / 负数 / 小数 / 非数字）一律**抛错**，
   绝不兜底取第 1 层 —— 「定点发第几层」配错等于把钱发给错误的人
5. 祖先链长度不足该层时**不产生记录且不抛错**：链路深浅由事件当时的网络结构决定，
   属运行期数据而非配置错误，方向上属于少发
6. `ruleSetConfigSchema` 同步在配置期拦截：`target: "ANCESTOR"` 必须声明 `ancestorLevel`、
   `ancestorLevel` 挂在 `SOURCE`/`PARENT` 上拒绝（不会生效）、`type: "LEVEL"` 配
   `target: "ANCESTOR"` 拒绝（LEVEL 本就遍历整链），保持「校验期通过 ⇒ 计算期不因
   `ancestorLevel` 抛错」

**示例配置**：
```js
// 只给祖先链第 3 层这一个节点发 3%（不遍历整链）
{ rewardId: "gen3", type: "DIRECT", target: "ANCESTOR", ancestorLevel: 3, rate: "3", skipRankZero: false }

// FIXED / CUSTOM 同样支持
{ rewardId: "gen2_red", type: "FIXED", target: "ANCESTOR", ancestorLevel: 2, fixedAmount: "50", skipRankZero: false }
```

⚠️ **接入提醒**：定点发放与 `PARENT` 一样受 `skipRankZero`（**缺省 `true`**）约束，
目标节点 `rankRate <= 0`（含未评级）时静默跳过。定点发放的比例挂在规则上、与目标等级无关，
因此通常应显式写 `skipRankZero: false`。

**兼容性说明**：**纯新增能力**，未使用 `ANCESTOR` 的既有规则集行为零变化。

**测试**：新增 12 例（定点发放计算 7 + 配置校验 5），当前 315 全绿。

### 2.11 补充能力：conditions 的受益人侧数据源 source（✅ 已解决 v4.0.0）

**背景**（docs/007 §六 第 12 项）：v4.0.0 之前，`rewardDefs.conditions` 的数据源被
**硬编码为事件对象**（`condition-evaluator` 只接受一个 `data` 参数，`reward-distributor`
在循环顶部用事件求值一次）。这意味着通用分佣里最常见的三类**受益人侧**门槛完全无法表达：

- 「只给 V2 以上的上级发佣」（读上级等级）
- 「上级团队业绩满 5 万才发」（读上级业绩）
- 「上级本月已达上限则跳过」（读上级累计）

宿主唯一的绕法是在调用引擎前自己过滤祖先链 —— 但那会同时改变 LEVEL 的水位口径与层号
（被剔除的层不再占位，其余层层号前移），发放金额随之改变，属于「绕过引擎改钱」。

**本次落地**（v4.0.0）：

1. `condition-evaluator.js` 引入命名数据源：`CONDITION_SOURCES = ["event","target"]`，
   `_resolveDataSource(condition, data, context)` 按 `condition.source` 从
   `context` 取数；**未声明 `source` 时用默认数据源（第 2 个参数）**，与 1.0.0 逐位一致
2. `reward-distributor.js`（2.5.0）分流两条路径：
   - 条件树中**不含** `source: "target"` 的 def → 仍走循环顶部的单次事件门槛（旧路径）
   - **含** `source: "target"` 的 def → 按**受益节点**逐个求值；`DIRECT`/`FIXED`/`CUSTOM`
     对目标节点求值一次，`LEVEL` 通过 `calculateLevelChain` 新增的 `nodeFilter` 逐层求值
   - 条件树**不按 source 拆分**（混在同一棵 AND/OR 树里的事件侧与节点侧条件无法拆），
     整棵树带 `{ event, target }` 两个命名数据源一起求值
3. `chain-calculator.js`（2.3.0）的 `nodeFilter`：被拦下的层用 `continue` 跳过 ——
   不发放、**不推进水位**、也不改变其余层的层号，与既有 `diffRate <= 0` 跳过**完全同一口径**
4. fail-closed 约束：未知 `source`、或声明了 `source` 但该数据源缺失，一律**抛错** ——
   静默回退到另一个数据源会把「该拦住」翻成「放行」，方向上是超发
5. `sourceNode`（事件来源节点对象）贯穿各层可选参数：`distributeByDefs` →
   `executePipeline` 的 DISTRIBUTE 阶段 → `buildPipelineStages` →
   `GenericSettlementService.buildSourceNode(event)` 钩子。`target: "SOURCE"` + 节点侧条件时
   引擎只有 `event.sourceNodeId`、没有节点对象，缺失时抛错提示传入 `sourceNode`；
   **不参与 RANK 阶段评级**（那会开始给事件来源节点写 `rankRate`，改变既有行为）
6. `ruleSetConfigSchema`（4.0.0）把 `conditions` 从 `Joi.array().items(Joi.object())`
   （= 完全不校验）改为**递归条件树校验**：用 `Joi.link('#id')` 递归、
   `alternatives().conditional('.type')` 按类型精确分派（`alternatives().try` 只会报
   "does not match any of the allowed types"，把 `source` 拼错这类资金笔误藏起来）。
   `rewardDefs` 允许 `source: "event"|"target"`，`rankDefs` **只允许 `"target"`**
   （等级评估没有事件上下文，写 `"event"` 运行期必抛错，配置期即拒绝）
7. 顺带修复：复合条件的 `children` 未写 `type` 时此前被判「不满足」→ 静默少发
   （调用方只在 `conditions` 数组顶层补 `type: "COMPARE"`）；现按 `field` 存在推断为
   `COMPARE`，与校验层接受的形状一致，`{}` 这类无字段对象仍判 `false`（未引入 fail-open）

**示例配置**：
```js
// 只给 V2 以上的上级发佣
{ rewardId: "p", type: "DIRECT", target: "PARENT", rate: "10", skipRankZero: false,
  conditions: [{ field: "vipLevel", operator: "GTE", value: 2, source: "target" }] }

// 事件侧 + 受益人侧混在同一棵树：订单满 1000 且上级团队业绩满 5 万
{ rewardId: "p2", type: "DIRECT", target: "PARENT", rate: "5", skipRankZero: false,
  conditions: [{ type: "AND", children: [
    { field: "orderAmount",     operator: "GTE", value: 1000,  source: "event"  },
    { field: "teamPerformance", operator: "GTE", value: 50000, source: "target" },
  ] }] }
```

⚠️ **接入提醒**：`field` 用**扁平字段名**（节点侧读取顺序 `node.attrs[field]` → `node[field]`），
不支持点分路径 —— 点分路径只在 `CUSTOM` 的 `amountFrom: "event.attrs.<path>"` 上支持。

**兼容性说明**：计算侧是**纯新增能力**（未写 `source` 的既有规则集行为零变化）；
校验侧是**有意的破坏性收紧** —— 此前能通过校验的错误 `conditions` 现在会报错。

**测试**：新增 22 例（distribute 的 source 数据源 10 + 条件求值 5 + 配置校验 5 +
适配器/流水线端到端 2），当前 337 全绿。
四道验证门全过：`npx jest` 337/337、`npm run smoke`、`node scripts/verify-pack.js`、
`tsc --strict`（含故意错误负对照）。
