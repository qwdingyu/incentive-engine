## 一、通用性评估：5-10 个营销/拉新/分佣项目的底座能力

### 1.1 已覆盖的能力矩阵

| 能力 | 说明 | 适用场景 | 覆盖率 |
|------|------|---------|--------|
| **DIRECT 百分比奖励** | 按 eventValue 的百分比给本人(SOLURCE) 或直接上级(PARENT) | 本人收益、直推佣金、一级分销 | ✅ 已实现 |

| **平台日封顶** | 当天平台总发放上限 | 企业预算控制 | ✅ 已实现 |
| **单用户日封顶** | 当天单个用户收到上限 | 防刷、防套利 | ✅ 已实现 |
| **预算兜底保护** | 按 eventValue 比例设总预算上限 | 活动预算控制、防配置错误超发 | ✅ 已实现（CAP/WARN/REJECT） |

| **复合条件** | AND/OR/NOT 组合条件树 | 复杂晋升条件 | ✅ 已实现 |
| **流水线编排** | 任意组合阶段 | 灵活的计算链路 | ✅ 已实现 |
| **灰度/A-B 测试** | Hash 加权版本路由 | 规则集灰度发布 | ✅ 已实现（Utils） |

## 二、能力缺口与扩展路线图

### 2.1 缺口 1：FIXED 固定金额奖励（✅ 已解决 v3.1.0）

**场景**：拉新奖励（拉一人奖 50 元）、人头奖励、固定红包

**当前状态**：已实现。引擎新增 `type: "FIXED"` + `fixedAmount`，`distributeByDefs` 支持 SOURCE/PARENT 两种 target，`calculateFixed` 提供单条计算，`ruleSetConfigSchema` 对 FIXED 类型强制校验 `fixedAmount > 0`（防误配）。

**实现内容**（本次落地）：
1. `RewardDef` 增加 `fixedAmount` 字段（DIRECT/LEVEL/FIXED/CUSTOM 四类型）
2. `direct-calculator.js` 新增 `calculateFixed` 函数（金额与事件值无关，沿用 skipRankZero 语义）
3. `distributeByDefs` 增加 FIXED 类型处理（SOURCE/PARENT + 未知 target 抛错）
4. `ruleSetConfigSchema` 允许 FIXED 类型，并通过 `.custom` 交叉校验强制 `fixedAmount > 0`
5. 引擎测试新增 9 例（6 个 distribute + 3 个 validation），170 全绿

**示例配置**：
```js
{
  rewardId: "referral_bonus",
  type: "FIXED",
  target: "PARENT",
  fixedAmount: "50",       // 固定金额 50 元
  skipRankZero: false,
}
```

### 2.2 缺口 2：WEEKLY/MONTHLY 封顶（中优先级）

**场景**：活动预算（周/月上限）、运营周期控制

**当前限制**：只支持 PLATFORM_DAILY 和 PER_USER_DAILY 两种封顶范围

**解决方案**（估算 1-2 人日）：
1. `capDefSchema` 增加 `WEEKLY`/`MONTHLY` 选项
2. `applyCaps` 增加周/月维度水位追踪
3. 调用方需提供周/月起始结算数据

### 2.3 缺口 3：活动期加成（中优先级）

**场景**：双十一加佣（活动期间佣金翻倍）、限时奖励

**当前限制**：规则集是静态配置，不支持日期范围的特殊比例

**解决方案**（估算 2-3 人日）：
1. 引入 `CampaignDef` 配置：`{ campaignId, dateRange, multiplier }`
2. `pipelineDef` 增加 `CAMPAIGN` handler
3. 在 DISTRIBUTE 阶段后对奖励金额乘以活动系数

### 2.4 缺口 4：退款/撤销（低优先级，一期不做）

**场景**：订单退款 → 回收已发放佣金

**当前限制**：引擎无"负事件"概念

**解决方案**（估算 3-5 人日）：
1. 引入 `EVENT_TYPE: "REVERSAL"` 事件类型
2. `Distribute` 增加逆向计算逻辑
3. 需要业务层配合：记录原始收益，按比例回收

### 2.5 缺口 5：多币种/多资产类型（低优先级）

**场景**：积分 + 现金 + 优惠券的组合奖励

**当前限制**：引擎只支持单一金额维度

**解决方案**（估算 3-5 人日）：
1. `rewardDef` 增加 `assetType` 字段
2. `Allocate.splitByTargets` 支持多资产类型拆分
3. 需要 DB 层的多资产科目支持

### 2.6 补充能力：RANK 等级评估纳入标准流水线（✅ 已解决 v3.2.0）

**背景**：v3.2.0 之前，等级评估（rankRate 推导）不是流水线的一环——宿主必须在调用引擎前
自行预计算并把 `rankRate` 写进节点，标准流水线只"消费"已就绪的 rankRate。这是一个独立验证的
工程缺口：等级评估逻辑被散落在各宿主的适配器里，无法复用。

**本次落地**（v3.2.0，与 FIXED 同级为 P0 必备项）：
1. `RewardDef` 的 `rankRate` 语义落地：`model/rank-def.js` 新增可选 `rankRate` 字段（等级关联分成比例，RANK 命中时写入节点）
2. 校验：`rankDefSchema` 接受 `rankRate`（0~1000，默认 "0"）；`pipelineStageSchema.handler` 白名单增加 `RANK`
3. `pipeline-orchestrator.js` 新增 `RANK` handler：
   - 内部按 `levelIndex` 升序排序后逐节点求最高等级（`getHighestQualifiedTier` 保持"最后一个合格等级"，升序保证取到最高）
   - 就地写入 `node.rankRate` / `node.rankId`（节点为对象引用，随后的 DISTRIBUTE 立即可见）
   - 默认**不覆盖**宿主已预计算的 rankRate；`overwrite: true` 才覆盖场景需显式声明
   - 节点未命中任何等级 → 落到 `rankRate: "0"`；本阶段不产生分发记录
4. `rule-set-adapter.js` 新增 `RANK` 阶段装配：自动注入规则集 `rankDefs`，默认评估 `directParent + ancestors`
   （过滤 null/无效节点、按 id 去重直接上级与祖先重叠及祖先内部重复的场景），支持 `stage.config.nodes` 显式覆盖与 `overwrite` 透传
5. 流水线示例：`RANK → DISTRIBUTE → CAP`（DISTRIBUTE 的 LEVEL 链式差额直接消费 RANK 写入的 rankRate）

**示例配置**：
```js
// pipelineDef.stages 声明 RANK 后，等级评估即成为标准流水线一环
{
  stages: [
    { handler: "RANK" },                                // 评估 directParent+ancestors，写入 rankRate
    { handler: "DISTRIBUTE", config: { /* rewardDefs 使用 LEVEL/动态消费 rankRate */ } },
    { handler: "CAP", config: { /* capDefs */ } },
  ],
}
```

**兼容性说明**：RANK 为**可选阶段**——仅当 `pipelineDef.stages` 声明 `handler: "RANK"` 才启用；
既有宿主（未声明 RANK、仍按旧式预计算 rankRate）行为零变化，完全向后兼容。
引擎测试新增 11 例（装配 3 + 编排 4 + 校验 4），当前 180 全绿。
