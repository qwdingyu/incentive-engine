## 坑 1：Decimal.js 的 toDecimalPlaces 不强制尾零

### 背景
引擎的 `decimal.js` 包装函数（mul/add/sub/pct）使用 `toDecimalPlaces(4, ROUND_HALF_UP)` 计算金额。

### 现象
`Decimal.mul("10", "20")` 返回 `"200"` 而非 `"200.0000"`。

### 原因
`Decimal.toDecimalPlaces(dp)` 会四舍五入到指定位数，但不会填充尾零。`toFixed(dp)` 才会填充尾零。

### 解决方案
- 使用 `Decimal.eq()` 比较金额，而非 `===` 字符串比较
- 需要尾零时使用 `Decimal.toFixed(value, 4)` 显式格式化
- 不要依赖金额字符串的尾零数量

### 建议
- 业务 Service 层：全程使用 `Decimal.eq`/`Decimal.gte`/`Decimal.lt` 比较
- 展示层：使用 `Decimal.toDisplay(value, dp)` 转 number
- 写 DB：使用 `Decimal.toFixed(value, 4)` 确保格式一致

## 坑 2：evaluateTier 的 levelIndex 兼容性

### 背景
`evaluateTier` 函数同时支持两种等级表示：
- RankDef 实例（含 `metadata` 字段）：`levelIndex` 来自 `tier.levelIndex`
- 遗留对象（如宿主自有的 `vip_tiers` 表）：`levelIndex` 来自 `tier.tier_level`

### 坑
旧版 `_getLevelIndex` 用 `tier.metadata` 判断格式，但传入plain object 时 `metadata` 为 `undefined`，导致 `tier.levelIndex` 被忽略，始终返回 `tier.tier_level || 0`。

### 修复
v2.2.1 修复为：
```js
function _getLevelIndex(tier) {
  if (tier.metadata) return tier.levelIndex;
  return tier.levelIndex ?? tier.tier_level ?? 0;
}
```

### 建议
- 新代码统一使用 RankDef 格式（含 `levelIndex` 字段）
- `metadata` 只存放业务扩展字段，不用于判断等级索引

## 坑 3：applyBudgetGuard 的精度损失

### 背景
`applyBudgetGuard` 的 CAP 模式下，先用 `Decimal.div(budgetLimit, totalAmount, 4)` 计算比例（4 位小数），再用 `Decimal.mul(amount, ratio, 4)` 计算缩减金额。

### 现象
当日金额较大（如 10 万+）时，比例被截断到 4 位小数，导致各条目的缩减金额之和略小于预算上限。

### 原因
两步运算都使用 4 位小数精度，中间比例精度损失在第二步被放大。

### 解决方案
- 引擎已使用 28 位全局精度，但显式指定 dp=4 会覆盖全局精度
- 可考虑：不指定 dp 让中间计算使用全局精度，只在最终结果时截断
- 对于金额差异在 0.01 以内的场景，实际影响可忽略

### 建议
- 对账时允许微小误差（如 0.01 以内）
- 如需精确分配，可使用 `compareAmounts("FIRST")` 做兜底补齐

## 坑 4：封顶水位的跨批次共享

### 背景
`applyCaps` 的 `state` 是引用对象，同一批次内后续记录自动看到已更新水位。

### 现象
跨批次调用时，如果调用方没有正确保存/恢复 `capState`，会导致：
- 批次 1 执行后 `state.platformPaid = "5000"`
- 批次 2 传入新的空 `state`，导致封顶重置，可能超发

### 解决方案
- 单批次内：引擎自动推进水位，无需额外操作
- 跨批次：调用方必须保存 `context.capState`，在下一批次传入
- 示例如 `yield-engine.service` 的 `capState` 跨批共享模式

> **推荐做法（v4.0.0 起）**：使用 `GenericSettlementService` 时，直接配置
> `loadCapState` / `saveCapState` 钩子即可自动持久化水位，无需手动保存/恢复：
>
> ```js
> const svc = new GenericSettlementService({
>   loadCapState: async () => await capStateRepo.load(),
>   saveCapState: async (capState, transaction) => {
>     await capStateRepo.save(capState, { transaction });  // 与收益记录同事务原子提交
>   },
> });
> ```
>
> 钩子成对配置后，跨事件、跨批次、跨进程重启的日封顶都连续生效；
> 未配置时行为与 3.4.x 一致（封顶仅单事件内），但日封顶并未真正生效。

### 建议
- 使用 `JSON.parse(JSON.stringify(context.capState))` 深拷贝保存/恢复
- 为避免 `Map` 序列化问题，`memberPaid` 可转为普通对象存储

## 坑 5：规则集灰度发布的路由一致性

### 背景
`selectVersionByRoutingKey` 使用 MD5 hash 分桶（0~99），按权重分配版本。

### 坑
- 路由依赖 `routingKey`（通常为会员 ID），会员 ID 变更会导致路由到不同版本
- 同一批次内如果一个会员触发了多个事件，都必须使用同一路由结果

### 解决方案
- 在批次开始时，根据 `routingKey` 确定版本，缓存到整个批次生命周期
- 会员 ID 不可变（一旦分配不可修改）

### 建议
- 灰度版本路由结果应在 `context` 中缓存，避免同一会员多次计算路由不同
- 灰度版本数量不宜超过 10 个（schema 已限制）

## 坑 6：金额字段类型一致性

### 背景
引擎的金额字段（amount/eventValue/limit/rate）以 `string` 类型传递。

### 现象
- `Decimal.mul("100", 5)` 能工作但类型不安全
- 数据库返回的 `DECIMAL` 类型可能是 `string` 或 `number`（取决于 ORM 配置）
- JSON 序列化时 `string` 金额会被保留为 `string`，前端可能需要转换

### 解决方案
- 调用方必须确保传入引擎的金额是 `string` 类型
- 数据库读取后统一用 `String(value)` 转换
- 前端展示时用 `Number(value)` 或 `parseFloat(value)` 转换

### 建议
- 在适配器层（`buildEvent`/`buildRecord`）统一做 `String(value)` 转换
- Service 层全程使用 `string` 类型，仅 Controller 层转 `number` 返回

## 最佳实践清单

### 金额处理
- [ ] 所有金额变量声明为 `string` 类型（JSDoc `@param {string}`）
- [ ] 使用 `Decimal.eq()` 比较金额，而非 `===`
- [ ] 从 DB 读取后立即 `String(value)` 转换
- [ ] 写入 DB 前用 `Decimal.toFixed(value, 4)` 格式化

### 幂等
- [ ] 业务事件必须有唯一键（订单号/交易号）
- [ ] 引擎不负责幂等，幂等由业务层的预读检查 + 唯一约束实现
- [ ] 收益计算使用 `UNIQUE(order_id, yield_date, member_id, income_type)` 防止重复落账

### 事务
- [ ] 余额变更必须使用事务 + 行锁
- [ ] 流水记录必须在同一事务中完成
- [ ] 引擎调用应在事务内，确保计算 + 落账原子性

### 测试
- [ ] 每个引擎模块有独立单元测试（74 个基准测试覆盖）
- [ ] 金额计算使用 `Decimal.eq()` 断言，不使用 `===`
- [ ] 边界情况：rate=0、amount=0、空数组、null 输入

## 坑 2：schema 允许但引擎不消费 = 静默不生效（资金安全陷阱）

### 背景
引擎的 joi schema 定义了 `rewardDef.conditions`、`capDef.onExceed`、`conditionSchema.operator` 等字段，但早期版本的分发器/封顶器**不读取**这些字段。

### 现象
- `rewardDef.conditions` 配置了"仅高额订单发佣金"，引擎静默忽视、照发不误（v3.4.0 前）
- `capDef.onExceed="ALERT_ONLY"` 配置了"超发仅告警"，引擎静默当作 REJECT 裁剪（v3.4.7 前）
- `conditionSchema.operator` 缺 `NE`，运营无法配置"不等于"条件（v3.4.7 前）

### 原因
schema 是"配置契约"，但分发器/封顶器是"执行逻辑"，两者由不同开发者维护，容易脱节。

### 解决方案
- **schema 与实现必须同步**：新增 schema 字段时，必须同时实现对应逻辑
- **契约测试**：用 schema 校验的配置必须能通过引擎执行（rbb 侧 `_computeDiff` 契约测试）
- **fail-fast**：配置了但引擎不支持的字段，应报错而非静默忽略

### 建议
- 新增引擎能力时，schema + 实现 + 测试 + 文档四者同步
- 用"配置了必须生效"作为验收标准

## 坑 3：按比例分配金额的累积误差（最大剩余法）

### 背景
`applyBudgetGuard` 的 CAP 分支按比例缩减金额，早期用包装层 `mul`（四舍五入到 4 位）。

### 现象
3 条记录各 100，预算 200，比例 2/3：朴素四舍五入得 66.67×3=200.01，**超发 0.01**。预算兜底本意防超发，自身却系统性超发。

### 原因
包装层 `mul`/`div` 默认 `toDecimalPlaces(4)`，各条独立四舍五入产生累积误差。

### 解决方案
- **最大剩余法**：按比例取 4 位 floor，差额按余数从大到小分配给余数最大的前 N 条（每条 +0.0001），保证求和精确等于预算上限
- 用裸 `decimal.js` 全精度计算比例，避免包装层 4 位精度不足

### 建议
- 任何"按比例分配后求和必须精确等于总额"的场景，用最大剩余法
- 不要依赖包装层默认 4 位精度做精确分配

## 坑 4：非数值字段的大小比较崩溃

### 背景
`condition-evaluator` 的 GTE/GT/LTE/LT 操作符直接 `Decimal.gte()`，非数值字段（如 `vip="V3"`）抛 `Invalid argument`。

### 现象
运营配置 `{ field: "vip", operator: "GTE", value: "V2" }`，引擎崩溃而非安全返回 false。

### 原因
GTE/GT/LTE/LT 假设字段是数值，但等级标识等字段是非数值字符串。

### 解决方案
- `_isNumeric` 判断：非数值字段的大小比较安全返回 false（条件不满足，跳过奖励）
- EQ/NE 支持数值（Decimal）与非数值（字符串）双模式
- 带空格数字（`" 2000 "`）需 trim 后比较（decimal.js 不接受带空格）

### 建议
- 条件评估必须对非数值字段健壮，不能崩溃
- 字段值统一 trim 规范化后再比较
